## Существующие и потенциальные проблемы
- Нет резервации, основные сервисы имеют по одному инстансу. Например, отказ единственного инстанса MES останавливает как расчёт стоимости заказов, так и взаимодействие с другими продавцами (по API).
  - Единственный инстанс БД работает и на чтение, и на запись, а некоторые запросы уже выполняются непозволительно долго.
  - RabbitMQ как единственный инстанс брокера, сообщений, который связывает все сервисы, является единой точкой отказа, отсутствует резервация.
- Нет горизонтального масштабирования, в том числе динамического
- В списке статусов заказа отсутствует промежуточный статус (или нескольких) вроде `PRICE_CALCULATION_STARTED`, означающего, что MES приняла заказ
- MES является узким местом: тяжёлые расчёты выполняются на том же инстансе, где открыт API наружу, и с которым работают операторы
- Заказы создаются через MES, а не через CRM, и могут пропадать: API расчёта открыт в MES, а заказы создаются в CRM по итогам сообщения из очереди от MES, таким образом при падении MES заказ не регистрируется в CRM.
- Внешний трафик не ограничивается и не изолирован
- Долго загружается страница MES у операторов, они видят новые заказы с опозданием, что при текущей модели вознаграждения уменьшает мотивацию операторов
- Возможно, есть проблемы с надёжностью взаимодействия по шине данных, и какие-то сообщения (заказы, например) могут пропадать
- Проблемы с автоматическим тестированием, ручной деплой в release и prod окружения приводит к задержкам выхода версий
- Отсутствие наблюдаемости системы: о проблемах в компании зачастую узнают уже постфактум от клиентов

## Инициативы
- Оптимизировать БД с заказами на чтение
  - Определить данные, необходимые для основных страниц, вызывающих замедление. Проанализировать запросы на наличие индексов или множества операций JOIN.
  - В зависимости от ситуации либо реализовать View для этих страниц, либо выделить отдельную БД для чтения.
  - Рассмотреть паттерн кэширования Refresh ahead с обновлением по событиям создания заказов или обновления их статусов
- Выделить систему расчёта стоимости в отдельный микросервис с горизонтальным масштабированием
- Разгрузить MES, добавив Backpressure и очередь расчётов, запрос помещается в очередь, и при успешной постановке в очередь запросу присваивается статус `WAITING_FOR_PRICE_CALCULATION`
  - API расчёта возвращает `202 Accepted`, а при переполнении очереди `429 Too Many Requests` с Retry-After
  - Диспетчеризация на первых этапах осуществляется за счёт брокера и воркеров расчёта, в дальнейшем может быть отдельный сервис
  - Также добавить прогресс расчёта (и уведомления об его изменении) и соответствующий статус (`PRICE_CALCULATION_STARTED`).
  - Уведомлять клиента об изменении статуса заказа (опционально)
- Внедрить кэширование самых новых заказов, подключить страницу MES к событиям, чтобы новые заказы сразу отображались у оператора (WebSocket/SSE), при этом необходимо обеспечить атомарность операции приёма заказа, для этого будет использоваться оптимистическая блокировка
- Улучшить прослеживаемость состояний заказов
  - Сделать отдельную страницу с заказами, срок по текущему шагу которых приближается к планируемому или превысил его.
  - Сделать отдельный список просроченных заказов для менеджеров, чтобы такие заказы не терялись
- Улучшить наблюдаемость
  - Добавить логирование и сбор метрик, особенно с сервисов, которые могут быть причиной потери заказов: очередь сообщений, MES.
  - Сделать трейсинг ключевых запросов от клиента (в том числе от клиентов, использующих API)
- Провести аудит RabbitMQ.
  - убедиться, что сообщения сохраняются на диск на случай падения шины данных, добавить DLQ, чтобы сообщения не пропадали, определить порог числа сообщений в DLQ и в Prometheus настроить алерт на его превышение
  - Поднять ещё один резервный инстанс RabbitMQ (сделать кластер из двух и более нод)
  - Проанализировать, не является ли шина данных узким местом, если является, то либо использовать горизонтальное масштабирование, либо перейти на более производительное решение
- Улучшить надёжность системы
  - Создать Read-реплику БД
  - Добавить резервный инстанс MES
  - Настроить Transactional Outbox, это исключит потерю заказов между записью в БД и попаданием события в очередь RabbitMQ.
- Добавить API Gateway и внешний API вынести в этот сервис для ограничения числа запросов в пиковые периоды и создания единой точки аутентификации внешних пользователей.
  - Для расчётов стоимости перенести точку входа из MES в CRM и ввести понятие "заявка на расчёт стоимости", таким образом загруженный MES не будет отвечать за регистрацию "заказа" (заявки на расчёт)
  - Добавить Rate limiter и квоты на число одновременных расчётов для клиентов
- Внедрить автоматизацию в CI/CD для деплоя в release и prod, автоматизировать тестирование (автоматизацию тестирования возьмёт текущий QA-инженер, так как он уже делал прототипы, что снижает риск сопротивления изменению)

### Целевая архитектура через пол года
Через полгода система выглядит следующим образом:

#### Входной трафик.
- Внешние продавцы работают с системой через API Gateway
- Rate limiting и квоты на клиента максимально безболезненно для клиента сглаживает пики.
- Пиковый внешний трафик не достигает MES и не может вывести его из строя.

#### Создание заказа.
- Заказ всегда регистрируется в CRM независимо от доступности MES.
- CRM публикует события в RabbitMQ через Transactional Outbox, поэтому заказ не может быть потерян между сохранением в БД и публикацией в очередь.
- RabbitMQ развёрнут кластером из двух и более нод
  - Очереди настроены на сохранение на диск (persistent)
  - для необрабатываемых сообщений настроены DLQ с алерт на рост их количества.

#### Расчёт стоимости.
- Расчёт полностью асинхронный: запрос на расчёт возвращает `202 Accepted`, заказ проходит статусы `WAITING_FOR_PRICE_CALCULATION`, а затем `PRICE_CALCULATION_STARTED`, после завершения расчёта переходит в статус `PRICE_CALCULATED`.
- При переполнении очереди клиенту возвращается ответ со статусом `429 Too Many Requests` с Retry-After.
- Очередь расчётов размещается в RabbitMQ, воркеры расчёта масштабируются горизонтально (в перспективе — выделенный pricing-микросервис).
  <br/>При необходимости внедряется система приоритизации или отдельные очереди для тяжёлых моделей
- MES с критического пути создания заказа снят.

#### Работа операторов.
- Дашборд (главная страница) MES работает на оптимизированной схеме БД (возможно, на read-реплике) и кэше
- Новые заказы доставляются операторам через WebSocket/SSE
- Приём заказа в работу атомарен (оптимистическая блокировка), что исключает двойное принятие заказа.
- Менеджеры видят отдельный список заказов с истекающим и просроченным сроком.

#### Наблюдаемость.
- Подняты инстансы Prometheus, Grafana, созданы необходимые метрики
- Присутствуют централизованные логи со сквозным идентификатором заказа и distributed tracing по цепочке "клиент → магазин/API → CRM → очередь → MES".
- Алерты срабатывают раньше, чем приходят жалобы клиентов.

#### Инфраструктура.
- Критичные сервисы имеют минимум по два инстанса,
- БД расширена до нескольких реплик, есть read-реплики для аналитических запросов
- Деплой в release и prod автоматизирован, регрессия покрыта автотестами.


### Три инициативы
1. Улучшить наблюдаемость.
<br/>Сейчас информация о проблемах в большой степени приходит от клиентов, иногда уже после потери контрактов.
<br/>Мониторинг, логи и трейсинг – относительно дешёвый и быстрый путь к пониманию проблем, а также это инфраструктура, без которой нельзя ни подтвердить гипотезы о причинах потерь, ни проверить эффект остальных изменений.
2. Добавить API Gateway и сделать точкой входа CRM, введя понятие "заявка на расчёт стоимости".
<br/>Это добавит учёт таких запросов и выведет MES с критического пути создания заказа/заявки, при его перегрузке или падении заказы продолжат регистрироваться и не будут теряться.
3. Разгрузить MES.
<br/>Backpressure и очередь расчётов с новыми статусами позволят уменьшить вероятность перегрузки MES.
<br/>Несмотря на синхронные расчёты до 30 минут, конкурирующие с операционной нагрузкой, ограничение поступающих запросов позволит избежать падения MES с предполагаемым простоем, пока расчёты соседствуют с операционной деятельностью.
<br/>Так как перенос расчёта в отдельный сервис – довольно долгая и сложная работа, асинхронная очередь с 202/429 и статусами решает это силами текущей команды гораздо быстрее, что не отменяет того, что вынос расчёта в отдельный микросервис (инициатива №10), который становится следующим логичным шагом.
