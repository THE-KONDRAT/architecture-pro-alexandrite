# Архитектурное решение по логированию
## С каких систем нужно собирать логи
Логи должны быть структурированными (в JSON), содержать сквозные поля: `timestamp`, `order_id`, `client_id` (где применимо), `trace_id`
Логировать необходимо CRM, MES, API Gateway, Shop API.

| Источник              | События                   | Уровень | Ключевые поля (помимо сквозных)                                         |
|:----------------------|:--------------------------|:--------|:------------------------------------------------------------------------|
| CRM, MES              | Смена статуса заказа      | INFO    | `client_id`, `status_old`, `status_new`, `init_from` (system/operator)  |
| API Gateway, CRM      | Регистрация заявки/заказа | INFO    | `client_id`, `channel` (shop/api), `result`                             |
| MES                   | Расчёт стоимости          | INFO    | `duration`, `polygon_count`, `polygon_bucket`, `result`                 |
| CRM                   | Публикация событий в шину | INFO    | `exchange`, `routing_key`, `moved_to_dlq`                               |
| MES                   | Потребление событий       | INFO    | `queue`, `ack/nack`, `moved_to_dlq`                                     |
| API Gateway, Shop API | Загрузка файла 3D модели  | INFO    | `file_size`, `result`                                                   |

## Мотивация
На текущий момент разбор любой проблемы начинается со слов клиента, и чтобы понять, что случилось внутри, необходимо вручную просмотреть логи нескольких сервисов, причём эти логи находятся в разных местах. Это занимает часы и требует доступа к продакшену у каждого разбирающего.
Централизованное структурированное логирование в связке с трейсингом даст:
- Единую точку поиска по order_id/trace_id
- Единый формат
- Единый срок хранения 
Поддержка и разработка будут видеть одну и ту же картину, а разбор перестаёт зависеть от конкретного человека и его доступов.

Ожидается следующее влияние:
- Благодаря возможности поиска по идентификатору заказа и наличию всех логов в одном месте и в одном формате сократится время диагностики обращения поддержки с часов до минут.
- Сократится время исправления инцидентов за счёт наличия логирования и трейсинга.
- Увеличится доля инцидентов, найденных до жалобы клиента благодаря алертам по росту ERROR или событию попадания в DLQ.
- Уменьшится число тикетов поддержки, требующих эскалации до разработки, если проблему можно решить простым поиском по логам.
- Уменьшится время онбординга новых разработчиков благодаря стандартизации логов.

### Приоритет систем
Логирование и трейсинг в первую очередь настраиваются для MES, CRM и API Gateway, так как именно на этой цепочке теряются заказы.
Следующим сервисом должен быть Shop API, так как хоть его сбои видны покупателю напрямую, но сейчас частично покрываются Яндекс Метрикой.

### Уровни логирования
| Уровень | Какие операции включает                           | Комментарий                                                                                                         |
|:-------:|---------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
|  DEBUG  | на усмотрение разработки                          | На проде только ручное временное включение на конкретном инстансе под разбор инцидента с автоматическим выключением |
|  WARN   | ретраи, таймауты, выдача 429, «расчёт дольше p95» |                                                                                                                     |
|  ERROR  | неуспешные операции, исключения, nack, уход в DLQ |                                                                                                                     |
|  FATAL  | падение процесса                                  |                                                                                                                     |

## Предлагаемое решение

Приложения пишут структурированные JSON-логи в stdout. Все логи имеют единый формат: `timestamp`, `level`, `service`, `order_id`, `trace_id`, `client_id`, `message`, поля события.
`trace_id` прокидывается из OpenTelemetry-контекста, что связывает логи и трейсы по одному идентификатору.
На каждой ноде кластера развёрнут Fluent Bit (DaemonSet), который собирает логи контейнеров, парсит JSON, обогащает служебными полями (namespace, pod), маскирует чувствительные данные и отправляет в OpenSearch по HTTP.
В роли хранилища логов выступает кластер OpenSearch (в будущем managed-вариант в облаке).
Визуализация и поиск выполняются с помощью OpenSearch Dashboards.
Алертинг происходит через встроенный плагин Alerting, уведомления дублируются в Alertmanager.

### Доработка сервисов
- MES (C#): использовать библиотеку Serilog с JSON-форматтером и Enricher'ом для trace_id/order_id
- API Gateway (Kong) настроить JSON-формат access/error-логов
- Internet Shop/CRM (Java) подключить Logback JSON


### Политика безопасности
- Маскирование персональных данных (телефоны, имена, e-mail и т.д.) осуществляется в первую очередь на уровне приложения, но дополнительно выполняется правилами Fluent Bit до записи в хранилище, таким образом в логах чувствительных данных либо вообще нет, либо остаются только хэши или маски
- Доступ к дашбордам разрешён только для сотрудников с ролью "Поддержка", доступ извне запрещён
- При передаче логов от Fluent Bit к OpenSearch используется шифрование TLS внутри кластера
- OpenSearch и Dashboards наружу не публикуются, доступ только из внутренней сети
- Действия пользователей в дашбордах аудируются

### Политика хранения
- Индексы разделены по системам: logs-crm-*, logs-mes-*, logs-gateway-*, logs-shop-*
- Настроена ротация: rollover при достижении 30 ГБ или 30 дней, далее можно скорректировать по использованию.
- Retention через ISM-политики (ISM – аналог ILM в Elasticsearch): горячие индексы 14 дней (далее перемещение в более дешёвое хранилище), удаление происходит через 90 дней.

Оценка размера логов
Предположения:
1. 10 событий на заказ
2. 1 КБ на событие
3. 300 заказов в день
4. Нагрузка ~20 RPS, генерирующих ещё около 1 кб логов на каждый запрос


Объём логов на расчётное количество заказов (10 событий \* 1 Кб \* 300 заказов/день \* {период (число дней)} + 20 \* 1 кб \* 86400)

| Период                     | Объём      |
|----------------------------|------------|
| День                       | ~1.65 Гб   |
| Месяц                      | ~49.44 Гб  |
| Горячие индексы (14 дней)  | ~23.08 Гб  |
| Срок жизни логов (90 дней) | ~148.32 Гб |

Минимально необходимо 150Гб, с полуторакратным запасом стоит ориентироваться на 220-250Гб. Если хранить горячие индексы на SSD, то необходимо выделить примерно 24 Гб, а с запасом – 35Гб, а на HDD нужно ~164 Гб
Оценка будет пересмотрена по итогам первых 180 дней по фактическим данным.

## Аналитика логов
Система сбора логов проектируется с расчётом на обеспечение их анализа. Для этого нужно уметь детектировать аномалии, высылать алерты и предоставлять сотрудникам удобные инструменты для ручного анализа.

Алертинг будет настроен сразу. На данных логов через Alerting-плагин OpenSearch настраиваются правила, а уведомления передаются в Alertmanager, откуда уже маршрутизируются в подходящий канал:
Алерты срабатывают в следующих случаях:
- Рост доли ERROR-логов любой системы за 5 минут выше базовой линии
- Событие попадания сообщения в DLQ (алерт высокого приоритета, так как это потенциально потерянный заказ)
- Потребление события из очереди (в MES) без последующего лога завершения расчёта в течение SLA означает зависание расчёта
- Всплеск выдачи 429 на API Gateway может выявить перегрузку внешнего контура и дать контекст, какой именно клиент стоит за этим

Аномалиями считаются:
- Резкий всплеск числа событий регистрации заказа. Такое отклонение от скользящей средней вероятно является признаком DDoS-атаки или ошибки у клиента API. В этом случае необходимо отправлять алерт и начинать автоматический сбор access-логов Gateway по этому окну для разбора
- Резкое снижение числа событий регистрации заказов может свидетельствовать о вероятной деградации API Gateway или CRM

Для команды будут созданы удобные дашборды с целью максимально быстро и точно диагностировать проблему:
- ERROR-rate по системам
- Топ-10 ошибок недели
- Длительность расчёта по polygon_bucket

Также необходимо раз в месяц проводить пересмотр порогов алертов по фактическим данным, чтобы снизить число ложных срабатываний или пропусков событий.

## Критерии для выбора технологии

| Критерий                                             | ELK                                    | OpenSearch                           | Splunk                     | Loki                                |
|:-----------------------------------------------------|:---------------------------------------|:-------------------------------------|:---------------------------|:------------------------------------|
| Лицензия                                             | Elastic License, часть функций платная | Apache 2.0                           | Проприетарная, платная     | AGPL                                |
| Экосистема (агенты, дашборды, алертинг)              | полная                                 | полная (Dashboards, Alerting-плагин) | полная, закрытая           | агенты есть, алертинг через Grafana |
| Полнотекстовый поиск (по order_id)                   | отличный                               | отличный                             | отличный                   | ограничен (индекс по меткам)        |
| Интеграция с текущим стеком (Prometheus/Grafana/k8s) | хорошая                                | хорошая                              | слабая                     | отличная (общий UI с метриками)     |
| Ресурсы и эксплуатация                               | тяжёлый                                | тяжёлый                              | тяжёлый, высокая стоимость | лёгкий, дешёвое хранение            |
| Масштабируемость                                     | высокая                                | высокая                              | высокая                    | высокая (объектное хранилище)       |
| Порог входа для команды                              | низкий                                 | низкий                               | высокий                    | средний                             |

Выбран OpenSearch, так как у него свободная лицензия Apache 2.0. У него зрелая экосистема (Fluent Bit пишет в него из коробки, Dashboards — аналог Kibana, встроенный Alerting), благодаря этому уменьшается сложность внедрения и снижается порог входа для новых сотрудников.
Полнотекстовый поиск по order_id на уровне ELK стека, а это главный сценарий использования системы, особенно на первых этапах, когда логирование будет помогать решать проблемы с потерянными заказами.
Loki проигрывает по полнотекстовому поиску и потребует обвязки через Grafana, а Splunk отпадает по стоимости и порогу входа.
ELK не подходит по лицензионным рискам: в последних версиях часть функций ушла в платную подписку.
Также рассматривался Manticore — быстрый движок с инвертированным индексом и российской командой разработки.
Может быть заменой ElasticSearch в ELK-стеке (интеграция с Kibana существует), но с существенными ограничениями:
- Поддерживается только версия 7.6.0
- Нет ILM
- Ограничены типы полей и агрегации (а в предлагаемом решении детекция аномалий и ERROR-rate строится именно на агрегациях)
- Экосистема и сообщество заметно меньше, чем у OpenSearch

Manticore на текущий момент не предоставляет полностью необходимый функционал.
