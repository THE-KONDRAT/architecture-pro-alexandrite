# Выбор и настройка мониторинга в системе
## Мотивация
Внедрение мониторинга – первый и необходимый шаг к решению накопившихся проблем.
Мониторинг систем позволит на этапе применения экстренных мер точно диагностировать проблемные узлы системы, а в будущем позволит предотвращать проблемы заранее до того, как клиенты почувствуют их на себе. Это позволит избежать как репутационных, так и финансовых издержек.
Существующий мониторинг через Яндекс Метрику не учитывает внешних продавцов, использующих API.

## Выбор подхода к мониторингу
Для всех сервисов с преимущественно сетевым взаимодействием без длительных тяжеловесных операций – RED (Internet Shop API, CRM API, API Gateway).
Для MES, БД и брокера сообщений (RabbitMQ) – USE, для MES добавить задержки.
Для диспетчера очередей – 4 золотых сигнала

## План действий
1. Развернуть Prometheus и Grafana.
2. Подключить экспортеры node_exporter, rabbitmq_exporter, postgres_exporter.
3. Добавить сбор метрик в приложения: Micrometer (Spring Boot: Shop/CRM), prometheus-net (C#: MES).
4. Реализовать кастомные метрики (длина очереди, возраст старейшего сообщения, взвешенная по полигонам, зависшие заказы).
5. Стандартизировать ярлыки.
   Ярлыки выбираются так, чтобы у команды были ответы на ключевые вопросы «кто генерирует нагрузку», «какой endpoint деградировал», «тормозят ли тяжёлые модели». Значения ярлыков не должны быть избыточно детализированными.
   Например, вместо точного числа полигонов используется polygon_bucket (`<10k`, `10k–100k`, `>100k`), а вместо `user_id` покупателей — `client_id` (компании).
   Обозначения ярлыков:
   - endpoint — точка входа API
   - method — HTTP-метод
   - client_id — идентификатор внешнего API-партнёра
   - instance — инстанс сервиса/БД
   - queue — имя очереди RabbitMQ
   - polygon_bucket — диапазон числа полигонов 3D-модели
   - order_status — статус заказа
6. Создать дашборды: "Состояние API" (RED), "Очередь расчётов" (кастомные метрики насыщенности очереди), "БД/RabbitMQ" (USE), "Зависшие и просроченные заказы" (для менеджмента).
7. Настроить алерты с эскалацией и пороги насыщенности.
8. Выработать цели по расчёту стоимости (например, p95 времени ожидания < 5 мин), скорректировать пороговые значения.

## Показатели насыщенности

| Memory любого критичного сервиса              | > 85%                                                                                                                           | Близко к OOM и переходу на swap, тоже может привести к деградации latency для операторов                                                      | Алерт в канал команды<br/>При продолжении роста создание тикета на расширение/анализ утечек                                                                     |
